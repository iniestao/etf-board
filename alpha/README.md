# ETF 因子计算：技术指标 + Alpha101

全市场 1717 只 ETF、154 万条日线，计算 **56 个技术指标 + 101 个 Alpha 因子**，
输出 Parquet 分片供云端查询。

| 项目 | 数值 |
|---|---|
| 标的 | 1717 只 |
| 行数 | 1,538,495 |
| 时间跨度 | 2005-02-23 ~ 2026-11-03 |
| 技术指标 | **56 个** |
| Alpha 因子 | **101/101 全部产出** |
| 计算耗时 | **221 秒**（单核，1737 万行×列运算） |

## 一、为什么是 Parquet on Object Storage

### 三种存储的实测对比

| 方案 | 体积 | 单只全字段读取 | 列裁剪 | 适合场景 |
|---|---|---|---|---|
| SQLite（现状） | 147 MB（仅 OHLCV） | 4.2 ms（9 字段） | 不支持，必须整行读 | 本地分析 |
| **Parquet + zstd** | **992 MB**（164 字段） | **6.8 ms** | **3.2 ms** | **云端分发** |
| CSV | ~4 GB | 慢 | 不支持 | ❌ |

字段数从 9 涨到 164（18 倍），读取时间只从 4.2ms 涨到 6.8ms——这就是列式存储的意义：
**查询只读需要的列**。画 K 线只需要 20 列，实际读取 3ms 左右。

### 为什么不用 Turso / D1

这两个都是 SQLite 系，看起来更「正统」，但算一下配额就排除了：

| | Turso | Cloudflare D1 | R2 + Parquet |
|---|---|---|---|
| 免费存储 | 9 GB ✅ | 5 GB ✅ | 10 GB ✅ |
| 写入配额 | 2500 万行/月 | **10 万行/天** ❌ | **100 万次 PUT**/月 |
| 每日全量刷新 | 154 万行 × 30 天 = **4600 万** ❌ 超 1.8 倍 | 需 15 天 ❌ | 1717 次 PUT × 30 = **5.1 万** ✅ |
| 出站流量 | 有限制 | 免费 | **完全免费** ✅ |
| 列裁剪 | ❌ | ❌ | ✅ |

关键在**每日全量重算**这个需求。因子必须每天重算（前一天的价格变化会影响所有滚动窗口），
154 万行写进去，Turso 的 2500 万写配额只够撑 16 天，D1 更是要 15 天才能写完一遍。

而 Parquet 方案是「整文件替换」：1717 个文件 PUT 一次，占月配额的 5%。

**R2 零出站流量费是决定性的。** 992 MB 数据集，用户每次打开页面拉一个 500KB 分片，
如果用 S3 或 Turso，出站流量费会随使用量线性增长；R2 不收这笔钱。

### 分片策略

```
dist/
├── etf/510300.parquet     每只一个文件，行=全历史交易日，列=164 个字段（993 MB）
├── etf/510050.parquet
├── ...                    共 1717 个
├── hist/510300.bin        近 500 天 × 17 字段，前端画 K 线用（46 MB）
├── hist/...               共 1717 个，约 36 KB/只
├── snapshot.parquet       1717 行 × 165 列，最新一日全市场截面
├── manifest.json          代码、名称、起止日期、字段清单、hist 格式元信息
└── ic_report.csv          101 个因子的 IC 检验结果
```

**为什么同一份数据导两个格式**：Parquet 给回测，`.bin` 给页面。

单只 Parquet 2.27 MB / 165 列，zstd 解压要几百毫秒，而 Cloudflare Workers 免费版
只有 10ms CPU——Worker 里解 Parquet 必然超时。所以另导一份无压缩定长二进制
（`magic + JSON header + int32 日期 + 17 列 float32`），Worker 只做 `bucket.get()`
后原样返回，浏览器端 `DataView` 切片成 `Float32Array`，不依赖 wasm、不依赖图表库。

字段只留画图要用的：OHLC、量额、`adj_ratio`、MA20/60、RSI14、MACD、布林上下轨、
ATR14、20 日历史波动率、5 日量比。价格存原始成交价（要跟券商软件对得上），
`adj_ratio` 乘上去就是前复权。格式细节见 `worker/README.md` 第三章。

单文件大小分布：

| 最小 | 25% | 中位 | 75% | 最大 |
|---|---|---|---|---|
| 23 KB | 227 KB | 473 KB | 833 KB | 3 MB |

### 压缩参数实测（拿 510300 的 3507 行 × 164 列做样本）

| 配置 | 体积 | 读取 | 判断 |
|---|---|---|---|
| zstd level 9 | 2206 KB | 5.4 ms | **当前选择** |
| zstd level 19 | 2190 KB | 5.4 ms | 只省 0.7%，不值 |
| gzip | 2195 KB | 5.9 ms | 无优势 |
| snappy | 2403 KB | 5.3 ms | 更快但更大 |
| 不压缩 | 2412 KB | 5.3 ms | — |
| **全转 float16** | **1245 KB** | 4.9 ms | 省 44%，但价格精度降到 3 位小数 |
| **只留 42 个显著因子** | **1524 KB** | 3.5 ms | 省 31%，代价是丢掉未显著因子 |

zstd 9 和 19 几乎一样，说明**数据的熵本身就高**——因子值是连续的浮点运算结果，
不像文本或重复 ID 那样可压缩。继续调压缩级别没有意义。

float16 能省 44%，但价格字段（4.092 这种）转 float16 后精度只剩约 0.004，
K 线图会出现可见误差。**当前保持 float32**：992 MB 在 R2 免费 10 GB 里占比不到 10%，
不值得为此牺牲精度。如果将来数据集大到需要瘦身，正确做法是「价格留 float32、
因子转 float16」，而不是一刀切。

**为什么按 code 分片而不是按日期？**
用户的使用模式是「打开某只 ETF 看它」，按 code 分片时一次只下载一个文件；
按日期分片则要扫遍所有年份文件才能拼出一只的完整曲线。

**全市场横截面查询**（如"按 Alpha018 排序找今天最值得买的"）走 `snapshot.parquet`，
只有 1717 行，6.5ms 读完，不需要扫全库。

## 二、Alpha101 实现说明

论文：Kakushadze (2016), *101 Formulaic Alphas*, arXiv:1601.00991

严格按原式实现，未做简化。三处必要偏离：

| 偏离 | 原因 | 影响因子 |
|---|---|---|
| `IndNeutralize` 用「资产类别」代理行业 | ETF 无申万分类 | 19 个 |
| `cap` 用成交额代理 | ETF 无市值概念 | a056 |
| 小数窗口取整 | 3.92795 天无意义 | a058-a100 部分 |

### IC 检验结果（前 12）

可投资域：当日成交额 ≥ 1000 万。不剔除僵尸 ETF 的话，IC 会被「不动的价格」稀释到 0。

| 因子 | IC 均值 | IR | t 值 | 胜率 | 有效天数 |
|---|---|---|---|---|---|
| **a018** | **−0.0261** | −0.101 | **−5.24** | 53.6% | 2671 |
| a032 | 0.0250 | 0.076 | 3.74 | 52.1% | 2397 |
| a060 | 0.0230 | 0.079 | 4.08 | 52.2% | 2673 |
| **a044** | **0.0220** | **0.144** | **7.46** | **55.0%** | 2677 |
| a085 | 0.0206 | 0.114 | 5.80 | 53.1% | 2595 |
| a006 | 0.0188 | 0.096 | 4.96 | 54.8% | 2673 |
| a039 | −0.0186 | −0.060 | −2.94 | 52.8% | 2369 |
| a040 | 0.0182 | 0.084 | 4.33 | 54.8% | 2671 |
| a054 | 0.0181 | 0.063 | 3.29 | 51.7% | 2696 |
| a014 | 0.0175 | 0.091 | 4.71 | 53.6% | 2673 |
| a073 | −0.0170 | −0.055 | −2.83 | 51.9% | 2684 |
| a093 | −0.0164 | −0.092 | −4.60 | 53.6% | 2524 |

**怎么读这张表**

- `IC 均值`：日频因子 0.02~0.03 是正常水平。研报里 0.03 就算不错，单一因子 0.02 可用但要组合。
- `IR = IC均值 / IC标准差`：衡量稳定性，比 IC 绝对值更重要。**a044 的 IR 0.144 是全库最高**。
- `t 值`：绝对值 >2 表示统计显著。共 **42 个**因子通过。
- 负 IC 不是坏事——反向用就是正向因子。a018 的 IC −0.0261、t −5.24，取负号后用。

### ETF 上特有的失效风险

`volume` 对 ETF 的含义与个股根本不同：ETF 份额可随时申赎，成交量主要反映
做市商和套利盘，而不是投资者看多看空。因此**约 60 个依赖 volume 的因子在 ETF 上
经济含义弱于股票**，需按 IC 筛选后再用。

实测证据：`ts_corr` 在流动性差的 ETF 上产生了 **8726 个 inf**——量能过于平稳时
相关系数分母为 0。这些已统一转成 NaN（"算不出相关性"比"相关性无穷大"更接近事实）。

## 三、56 个技术指标

| 类别 | 指标 |
|---|---|
| 趋势 | MA(5/10/20/60/120)、EMA(12/26)、MACD(DIF/DEA/柱)、DMI(PDI/MDI/ADX)、Aroon、TRIX、BIAS(6/12/24) |
| 动量 | RSI(6/14/24)、KDJ(K/D/J)、Williams %R、ROC、MOM、CMO、TSI、终极摆动、CCI、PSY |
| 波动 | ATR、NATR、布林带(上/中/下/%B/带宽)、肯特纳通道、唐奇安通道、历史波动率(20/60)、Parkinson 波动率 |
| 量能 | OBV、A/D 线、CMF、MFI、VR、量比、成交额强度、Amihud 非流动性 |

价格类指标一律用**后复权价**计算。不复权的话，每次分红都会被当成真实下跌——
510300 十四年累计分红 0.88 元，对 4 元的价格是 20% 的假跌幅。

## 四、云上部署（一步到位）

### 架构

```
GitHub Actions（每日 16:35，cron）
  ├─ 拉新浪全量历史（1717 只 / 18 页）
  ├─ 算复权（分红 + 174 次份额折算）
  ├─ 算 56 指标 + 101 因子
  ├─ 内部 IC 检验（可选，用于筛选）
  └─ aws s3 sync → Cloudflare R2
                    │
                    ├─ etf/{code}.parquet      1717 个分片
                    ├─ snapshot.parquet         全市场截面
                    └─ manifest.json
                              │
Cloudflare Workers ───────────┤
  ├─ GET /               前端单页
  ├─ GET /api/quotes     实时行情（代理新浪，5s 缓存）
  └─ GET /data/*         反代 R2（可选：直连 R2 自定义域名更快）
```

**为什么重计算放 GitHub Actions 而不是 Worker**
Workers 免费版限每请求 10ms CPU，而全量计算要 221 秒。Actions 免费 2000 分钟/月，
每天跑一次 4 分钟 = 120 分钟/月，占 6%。

**为什么 Worker 只做薄代理**
纯转发不消耗 CPU 配额，10ms 限制不再是瓶颈。之前担心的 CPU 问题，
在「计算下沉到 Actions」之后自动消失了。

### 需要注册的账号

| 平台 | 用途 | 注册方式 | 信用卡 |
|---|---|---|---|
| **GitHub** | 代码托管 + Actions + 作为 CI 身份 | 邮箱 | 不需要 |
| **Cloudflare** | R2 存储 + Workers | 邮箱 | 不需要 |
| Cloudflare R2 密钥 | Actions 上传凭证 | 控制台生成 Access Key | — |

Deno Deploy / Turso **不需要**——重计算已下沉，它们解决的问题在这里不存在。

### 配置步骤

1. **建 R2 Bucket**：Cloudflare 控制台 → R2 → Create bucket → `etf-data`
2. **生成 R2 密钥**：R2 → Manage R2 API Tokens → Create token（权限 Object Read & Write）
3. **GitHub 仓库 Secrets** 加四项：
   ```
   R2_ACCOUNT_ID          账户 ID
   R2_ACCESS_KEY_ID       密钥 ID
   R2_SECRET_ACCESS_KEY   密钥
   R2_BUCKET              etf-data
   ```
4. **推送代码**，Actions 自动跑第一次
5. **建 Worker**，绑定 R2 bucket

详细操作见仓库 `.github/workflows/update-data.yml` 与 `worker/`。

## 六、因子相关性聚类与样本外验证

```bash
python select_factors.py --years 3 --topn 8 --thresh 0.5
```

流程：算 101×101 横截面相关矩阵 → 层次聚类 → 按训练段 IC 贪心选因子（强制两两低相关）
→ 训练段定权重、测试段回测 → 输出报告。

**结论是不太好看的，但必须记下来：**

| 阶段 | 结果 |
|---|---|
| 因子相关性 | pairwise 均值 **0.101**、中位 0.056，仅 1.0% 的因子对 > 0.6。**没有共线性问题** |
| 聚类 | 73 个簇，其中 60 个只有 1 个因子 |
| 训练段（435 日）多空 | 8 因子 **+11.9%（夏普 1.21）**、101 因子 **+15.0%（夏普 1.61）** |
| 测试段（291 日）多空 | 8 因子 **−9.5%（−0.67）**、101 因子 **−10.0%（−0.71）** |
| IC 持续性 | 训练/测试 IC 相关 **0.184**，符号一致率 **53%**（≈抛硬币） |

样本内夏普 1.6、样本外 −0.7。**这说明因子在 ETF 上的横截面 IC 强度低于它的时间漂移**，
不能当交易信号用。完整分析（含为什么、还能怎么用）见 [`../docs/FACTORS.md`](../docs/FACTORS.md) 第 4~6 章。

输出：`dist/factor_corr.parquet`、`factor_clusters.csv`、`factor_combo.json`、
`combo_backtest.csv`、`corr_heatmap.png`、`combo_nav.png`。

## 七、已知限制

| 项 | 说明 |
|---|---|
| 内存 | 全量计算峰值 6.6 GB，Actions 标准 runner 有 7 GB，**刚好够但没余量**。若加因子需降级为分批计算或减少时间跨度 |
| a097 | 覆盖率仅 15%：需要 121 天连续有效数据，且中间不能有零成交断点 |
| a101 | 用复权价算，而公式分母有 `+0.001` 常数，导致与「原始价手算」差约 0.3%。对排序几乎无影响（该因子 IC 0.009 本就不显著），若要严格可单独用原始价重算 |
| 因子共线性 | **实测并不高**：pairwise 相关性均值 0.101、中位 0.056，只有 1.0% 的因子对超过 0.6。原本预期 a058~a100 高度共线，实测族内均值仅 0.074。这是衰减偏差（信号弱 → 观测相关被噪声压低） |
| 因子有效性 | **样本外不可用**。训练段多空夏普 1.21~1.61，测试段 −0.67~−0.71；训练/测试 IC 相关仅 0.184，符号一致率 53%。详见 `docs/FACTORS.md` 第 5 章 |
| 未来函数 | 所有因子只用当日及之前数据；`fwd` 收益用于 IC 检验时已 `shift(-h)`，不会泄漏 |
