# ETF 历史数据管道

盯盘页只能看当下。要算技术指标、跑策略回测，必须先有一份**干净、完整、可复权**的历史库。这个目录就是干这个的。

## 一句话架构

```
新浪 klc_kl.js（全历史 OHLCV+成交额）  +  hfq.js（分红记录）
        │  本地一次性导入，约 10 分钟
        ▼
   etf.db  (SQLite，全市场 1717 只)
        │
        ├─→ Python / DB Browser：自由查询、指标、回测
        └─→ 可选上云（Turso / R2）：网页也能看历史图
```

## 快速开始

```bash
# 1. 全市场导入（需要 Node >= 22.5，零依赖）
node import_etf.mjs

# 2. 试跑，只导 30 只
node import_etf.mjs --limit 30 --out test.db

# 3. 重跑失败的部分（跳过已完成的）
node import_etf.mjs --resume

# 4. 只更新指定的几只
node import_etf.mjs --codes 510300,513180 --out etf.db
```

跑完得到 `etf.db`。用任意 SQLite 客户端打开：

```bash
sqlite3 etf.db < queries.sql      # 一次跑完所有示例
```

买入持有 96.4% 与后复权的总收益完全对上，说明复权链路是通的。双均线在这种宽基 ETF 上跑输买入持有 68 个百分点——这类策略反复被震荡打脸，是常见结论，不是数据问题。

内置 `load()` / `add_ma()` / `add_rsi()` / `add_macd()` / `add_atr()` /
`backtest()` / `perf()`，都是纯 pandas，没有额外依赖，可以直接抄进自己的框架。

**两个容易踩的点，脚本里已经处理**：

1. `load()` 默认返回后复权价 `close_adj`，回测必须用它，不能用 `close`。
2. `backtest()` 里 `pos = signal.shift(1)`——信号**次日生效**。不 shift 就是未来函数，回测会虚高到离谱。

## 数据源实测（2026-11 沙箱环境）

| 源 | 历史长度 | 格式 | 结论 |

**为什么不用 `getKLineData`**：它只给最近 1023 个交易日，且没有日期参数可以往前翻。做回测时 4 年常常不够——2015 年那波、2018 年熊市都拿不到。`klc_kl.js` 是唯一能给全历史的免费源，代价是需要解密。

### 解密怎么来的

`klc_kl.js` 返回 `var KLC_K2_sh510300="K2/3L5l4v3cpH..."` 这样的密文，解码函数是新浪前端自己的 JS。本目录的 `sina_klc_decode.js` 来自 [akshare](https://github.com/akfamily/akshare) 的 `stock/cons.py`（`hk_js_decode`），逻辑未做改动，只包成 ESM 模块。**纯函数，不联网，不发请求。**

## 表结构

```sql
etf_meta      -- 每只 ETF 的元信息
  code, name, exchange, first_date, last_date, bars, divs, updated_at

etf_daily     -- 日线（核心表，WITHOUT ROWID 省空间）
  code, date, open, high, low, close, volume, amount, adj_factor
  PRIMARY KEY (code, date)

etf_dividend  -- 分红记录
  code, date, div
  PRIMARY KEY (code, date)

etf_adjust    -- 复权事件全记录（分红 + 份额折算），可审计
  code, date, kind('div'|'split'), value, step
  PRIMARY KEY (code, date, kind)
```

字段口径：

| 字段 | 单位 | 说明 |
|---|---|---|
| `volume` | 股 | 新浪原始值，**不是手** |
| `amount` | 元 | 成交额 |
| `adj_factor` | 倍数 | **后复权因子**，最早交易日为 1，随时间递增（遇缩股则递减） |

## 复权：为什么必须做

ETF 每年分红，除权日价格会跳空。510300 在 2026-01-19 除权，前一天收 4.859，当天开 4.737，**凭空跌掉 2.5%**。

不复权直接算 MA，会把这次分红当成真实下跌；回测跨分红持仓，会少算 2% 收益。14 年累计分红 0.88 元，对 4 元的价格是 20%——不复权的回测结论基本没有意义。

**算法**：某事件日 `d` 的乘子 `step`，某交易日的后复权因子 = 该日之前所有 `step` 的**前缀积**（最早日 = 1，随时间递增）。

| 事件 | 乘子 | 说明 |
|---|---|---|
| 分红 | `前收 / (前收 − 分红)` | 分红使价格下跌，后续价格要乘回去 |
| 份额折算 | `前收 / 折算后开盘` | 口径整体缩放，统一成「老价格 ÷ 新价格」 |

两者都是「把新口径价格还原回老口径」的倍数，所以可以直接连乘。

**验证**（510300 分红）：

| 除权日 | 累计分红变化 | 理论跳空 | 实际跳空 |
|---|---|---|---|
| 2026-01-19 | 0.757 → 0.880，本次 0.123 | −0.123 | **−0.122** |
| 2025-06-18 | 0.669 → 0.757，本次 0.088 | −0.088 | −0.086 |
| 2024-01-18 | 0.600 → 0.669，本次 0.069 | −0.069 | −0.074 |

**因子方向很容易搞反，这里踩过一次坑**：如果按「后缀积」做（把因子乘在事件日**之前**的 bar 上），510300 十四年收益会算成 **26%**，而实际含分红再投资是 **96.4%**（原始价格涨幅 57.1%）。分红收益被整个吃掉了。

| 算法 | 510300 总收益 |
|---|---|
| 原始价格（不复权） | +57.1% |
| ❌ 后缀积（方向反了） | +26.3% |
| ✅ 前缀积（正确） | **+96.4%** |

代码里 `adjFactors()` 的注释写明了这一点，改之前先读那段。

### 份额折算：一个必须单独处理的坑

ETF 会做**份额折算**（净值归一），比如把 2.24 元的净值改成 8.10 元、份额相应减少。价格在 K 线上直接跳变，但**持有人权益没变**。

`hfq.js` **只记录分红，完全不记录折算**。全库实测有 **174 次折算，涉及 161 只**，单日跳空幅度从 0.32 倍到 10 倍不等：

| 代码 | 日期 | 前收 | 折算后开盘 | 表观涨幅 | 实际是 |
|---|---|---|---|---|---|
| 510500 | 2015-04-15 | 2.243 | 8.100 | **+248%** | 1:3.6 折算 |
| 511030 | 2025-03-19 | 10.495 | 104.946 | **+900%** | 1:10 折算 |
| 159220 | 2025-11-10 | 1.240 | 0.616 | **−50%** | 1:0.5 折算 |

不处理的话，回测会把 510500 在 2015 年那天当成涨了 248%，结论彻底失真。

**识别方法**：A 股 ETF 有 10% 涨跌停，跨境/商品也不例外，所以单日跳空超过 ±30% 必然是折算而非真实行情。阈值取 `1.3 / 0.77`，修正后的连续性：

| 代码 | 修正前跳空 | 修正后跳空 | 类型 |
|---|---|---|---|
| 510500 | +248% | **−3.5%** | 1:3.6 缩股 |
| 511030 | +900% | **+0.05%** | 1:10 缩股 |
| 159922 | −60% | **−3.5%** | 分红 + 1:0.4 扩股（同日） |
| 512690 | −46% | **−0.8%** | 大比例分红（26%） |

注意 159922 这种**同一天既有分红又有折算**的情况：分红只能解释 2%，剩下 60% 的跳空是折算。所以检测时要先扣掉分红能解释的部分，剩下的残余跳空才归给折算——否则会被「当天有分红」这个条件直接跳过（这里踩过坑）。

所有折算事件都写在 `etf_adjust` 表里（`kind='split'`），可以直接查「这只 ETF 什么时候折算过」。

**注意因子不再恒 ≥ 1**：遇到缩股（份额合并、价格上跳），因子会小于 1。510500 的因子从 1 降到 0.2933，这是正确结果——它把 2015 年以来上涨的 3.6 倍折算还原掉了，露出真实的 92.9% 收益。

用法：

```sql
-- 后复权价（用于算指标、回测）
close * adj_factor

-- 前复权价（用于画图，与当前价格对齐）
close * adj_factor / (SELECT adj_factor FROM etf_daily WHERE code='510300' ORDER BY date DESC LIMIT 1)
```

`analyze_example.py` 的 `load(adjust='hfq'|'qfq')` 已经封装好这两种口径。

## 份额历史（`shares/`）

日线库之外还有一份**每日份额**：`shares/sz_hist.json`（772 只深市）+ `shares/sh_hist.json`（928 只沪市），各 265 个交易日，用来算「份额变化 / 净申购金额」。

```bash
python3 tools/xlsx2shares.py 深市ETF历史份额.xlsx -o data/shares/sz_hist.json --stats  # 深市（一次性，不再导）
python3 tools/sse_hist.py --date 2026-11-11                                              # 沪市增量
python3 tools/sse_hist.py --days 60                                                      # 沪市补最近 60 天
```

份额单位和日线不同：**这里存的是「份」**，不是手也不是元。净流入金额 = Δ份额 × 收盘价，在派生层算。格式、核对结果、已知坑都写在 [`shares/README.md`](shares/README.md)。

一句话记住：**沪市可回溯、可重抓；深市只有这份历史，日常增量从上线当日起攒。**

## 每日更新

收盘后（15:30 之后）重跑一次即可：

```bash
node import_etf.mjs --out etf.db
```

全量重拉约 10 分钟。**为什么不做增量**：`klc_kl.js` 只提供全历史，没有「只给最近 N 天」的参数，所以增量拉取省不了多少。全量重写反而保证数据一致（幂等，可重复跑）。

如果需要更快，加 `--delay 30` 能把时间压到一半，但触发风控的概率会上升。

## 上云（可选）

本地库已经够做所有分析。只有想在**网页上**看历史 K 线时才需要上云。

| 方案 | 免费额度 | 首次导入 190 万行 | 结论 |
|---|---|---|---|
| **Turso**（libSQL） | 9 GB / 2500 万写/月 | 一次导完，占月配额 7.6% | ✅ 推荐 |
| Cloudflare D1 | 5 GB / **10 万行写/天** | **要 19 天** | ❌ 官方明确 wrangler 导入也计数 |
| Neon / Supabase | 0.5 GB | 存不下（含索引） | ❌ |
| Cloudflare R2 | 10 GB / 100 万写/月 | 按只分片，1717 个文件 | ✅ 但不支持 SQL |

D1 的问题在 2026-09-01 后变成了硬失败：当日写超 10 万行直接报错，次日 UTC 零点才恢复。官方 FAQ 明确「dashboard、wrangler、REST 的写入都计入 rows_written」，所以**分批导入也救不回来**。

Turso 导入：

```bash
turso db create etf
sqlite3 etf.db .dump | turso db shell etf      # 或用 turso db import
```

## 已知限制

- **只有日线**，没有分钟线。分钟级回测需要另找源（新浪 `scale=5/15/30/60` 只给最近 1023 根）。
- **已退市 ETF 拿不到**：新浪只对在市品种提供 `klc_kl.js`。列表里 1717 只包含部分停止交易的，导入时会 404 或返空，会被跳过并记入失败列表。
- **分红数据是差分推算**：`hfq.js` 给的是「累计每份分红」，本次分红 = 相邻两条差值。若某只 ETF 的首条分红记录早于其上市日，早期分红会漏算（实测 510300、510050 均完整）。
- **不含 IOPV / 溢价率历史**：那需要东财，境外 IP 拿不到。
- 数据仅供研究，**不构成交易依据**。真要下单前和券商终端核一次价。
