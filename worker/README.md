# 部署到免费云

覆盖境内上市全部 ETF（1717 只），含跨境 / 债券 / 货币 / 商品。
实时榜单 + 同指数去重 + 历史 K 线 + 自选跨设备，全部跑在免费额度内。

```
worker/
├── src/index.js        后端：多源竞速 + 透传 + 历史数据（R2 或 GitHub）+ KV 自选
├── src/page.js         前端：解析/分类/排序/去重/K 线面板 + 腾讯直连
├── src/idx_data.js     指数映射（由 pipeline/gen_idx_data.mjs 生成，勿手改）
├── dist/worker.js      单文件版（可直接粘贴部署）
├── deno/main.ts        Deno Deploy 入口
├── build.mjs           打包脚本
├── dev_server.mjs      本地调试（带 R2 / KV 的 mock）
└── wrangler.toml       可选绑定：R2（加速，需绑卡）、KV
```

## 一、数据源架构

| 用途 | 源 | 通道 | 频率 |
|---|---|---|---|
| 全市场 1717 只榜单 | 新浪 `etf_hq_fund` | Worker 代理（透传，不解码） | 60s / 非交易 300s |
| **自选盯盘** | **腾讯 `qt.gtimg.cn`** | **浏览器 `<script>` 直连** | **5s / 非交易 30s** |
| 溢价率 / IOPV | 东财 `push2delay` | Worker（东财可用时） | 跟随全市场 |
| 历史日线 + 指标 | GitHub `data` 分支（或 R2） | Worker 透传 → 浏览器解析 | 日更（Actions） |

### 为什么自选走浏览器直连腾讯

腾讯返回的是 `v_sh510300="1~名称~现价~..."` 这种 JS 赋值语句，且响应头带 `charset=GBK`。

- **Cloudflare Worker 里用不了**：Workers 的 `TextDecoder` 只支持 UTF-8，解 GBK 会抛异常
- **浏览器里完全可用**：`<script src>` 加载外部 JS 时，浏览器按响应头 charset 自动用 GBK 解码，中文完全正常（实测 `沪深300ETF华泰柏瑞` 无乱码）；而且 `<script>` 不受 CORS 限制

于是得到一条**零成本高频通道**：不经过 Worker、不消耗请求额度、不受 10ms CPU 限制，
5 秒刷一次也没有任何费用，腾讯 88 个字段全部可用。

> 溢价率需要 IOPV，只有东财提供。境外 IP 下东财大概率不通，溢价率列显示 `-`，不影响其他功能。

## 二、同指数去重（默认开）

### 2.1 为什么需要

1717 只 ETF 背后只有 476 个跟踪指数，同一个指数常常有一二十只 ETF 在同时交易：

| 跟踪指数 | ETF 只数 |
|---|---|
| 中证A500 | 40 |
| 沪深300 | 29 |
| 中证500 | 29 |
| 上证科创板综合 | 23 |
| 上证科创板50 | 20 |
| 中证全指证券公司 | 17 |
| 创业板指 | 17 |

它们跟踪同一个指数，日内涨跌幅几乎一样，差别只在跟踪误差、费率和盘口厚度。
榜单里连着排 40 行 A500，看着热闹，实际只有一个信息。按成交额留一只，**1717 → 515 只**。

> 这里只解决「不要重复看同一只指数」。同指数 ETF 之间的切换套利不在范围内——
> 那需要盘口逐笔、申赎清单和实时折溢价，不是一个盯盘表格能承担的。

### 2.2 怎么判定「同一指数」

不能靠名字匹配。`300ETF`、`沪深300ETF华泰柏瑞`、`300基金` 是同一只指数，
而 `沪深300价值`、`沪深300成长` 不是；`中证A500` 和 `中证A50` 差一个 0，完全无关。

映射取自天天基金基金档案页的 **「跟踪标的」** 字段，逐只抓取后归一化：

```bash
node pipeline/fetch_index_map.mjs    # 1717 只，约 75 秒；增量，已抓过的跳过
node pipeline/gen_idx_data.mjs       # → worker/src/idx_data.js（19KB）
```

归一化只做三件事：

1. 去掉括号注释：`创业板指数(价格)` → `创业板指数`
2. 剥末尾修饰：`指数` / `价格` / `全收益` / `人民币`（**注意顺序**，先剥"指数"再剥"价格"，
   否则 `上证科创板综合价格指数` 会被留下 `…综合价格`，同一指数拆成两组）
3. 查一张人工核对过的别名表：`上证科创板综合价格` → `上证科创板综合`

**只有官方指数全称确实相同的才合并。** 合并错了会把一只好标的从表里挤掉，
少合并只是多显示一行——代价不对等，所以这里一律保守。

### 2.3 交互

| 操作 | 效果 |
|---|---|
| 默认 | 每组只留成交额最大的，名称后显示 `×N`（该指数共 N 只），蓝色 = 本组代表 |
| 点 `×N` | 展开该指数全部成员，按成交额排序，再点一次返回 |
| 点「同指数去重」 | 关掉，显示全部 1717 只（状态存 localStorage） |
| 搜索时 | 自动不去重——搜 "300" 就是想看所有 300ETF，藏掉 28 只反而碍事 |

两个实现细节：

- **15% 滞后**：两只成交额接近时（5000 万 vs 5100 万），若每次刷新都按最大值选，
  60 秒一次就会来回跳，看着像在闪。现任只要还有最大值的 85% 就不换。
- **盘前用规模兜底**：9:15 前成交额全是 0，此时退到流通市值选代表标的。

单只的指数（229 个）不参与去重，也不进 `idx_data.js`，省体积。

### 2.4 映射过期怎么办

新 ETF 上市后映射会慢慢失效——新代码不在表里，就按"无跟踪标的"处理，不去重，不会出错。
Actions 每天跑一次覆盖度体检，低于 90% 会打 warning。真掉下去了，重跑上面两条命令
再部署一次即可，季度级别的维护频率。

## 三、历史 K 线

### 3.1 数据是怎么到浏览器手上的

```
GitHub Actions（每日 16:35）
  ├ 拉 1717 只全历史 → SQLite → 复权 → 56 指标 + 101 因子
  ├ dist/etf/{code}.parquet   全历史 × 165 字段，给回测用（993MB）
  └ dist/hist/{code}.bin      近 500 天 × 17 字段，给页面用（46MB）
        ↓ git push --force（孤儿单提交，仓库不膨胀）
      GitHub data 分支
        ↓ Worker 原样透传（不解压、不解析）
      浏览器 DataView → Float32Array → canvas
```

**为什么单独导一份 `.bin`**：单只 Parquet 是 2.27MB / 165 列，光 zstd 解压就要几百毫秒，
而 Workers 免费版只有 10ms CPU。硬解必然 1102 超时。所以换成定长二进制，
Worker 只做一次 `bucket.get()` + 流式返回，解析全部交给浏览器。

### 3.2 文件格式

无压缩、小端、定长。**压缩在这里是负收益**——46MB 走 Cloudflare 出站免费，
省下的带宽还不够多花一次解压的时间。

```
magic      4B    'ETH1'
hdr_len    4B    uint32，JSON header 字节数
header     nB    {"code","n","cols":[...17 个列名...],"start","end"}
dates      4B×n  int32，YYYYMMDD
列数据     4B×n×17  float32，按 cols 顺序逐列连续
```

列名写在 header 里而不是前端硬编码：以后加字段，旧文件不会静默错位。

| 字段 | 说明 |
|---|---|
| `open` `high` `low` `close` | 交易所原始成交价（不是复权价，要跟券商软件对得上） |
| `volume` `amount` | 成交量、成交额 |
| `adj_ratio` | `adj_factor / 最新日 adj_factor`，乘上去就是前复权价 |
| `ma20` `ma60` | 均线（已按前复权口径换算） |
| `rsi14` | 相对强弱 |
| `macd_dif` `macd_dea` | MACD |
| `boll_up` `boll_low` | 布林带上下轨 |
| `atr14` `hvol20` | 真实波幅、20 日历史波动率（**百分数**，14.55 表示 14.55%） |
| `vol_ratio5` | 5 日量比 |

单只约 36KB（500 天），全部 46MB。

### 3.3 交互

| 操作 | 效果 |
|---|---|
| 点任意一行（自选或榜单） | 弹出面板，默认 1 年 |
| 3M / 6M / 1Y / 全部 | 切换区间，最多 500 天 |
| 鼠标移动 | 十字光标 + 当日 OHLC / 涨跌 / 量额 / RSI |
| Esc 或点遮罩 | 关闭 |

区间概览里的「累计」有两个口径：**默认给复权收益**，括号里附原始价收益。
两者差异超过 0.5% 时会额外提示"本区间内有分红或份额折算"——
159922 就是典型，原始价算出来 −56%，复权后其实是 +10.9%。

### 3.4 两种数据源

`histSource()` 按优先级选源：绑了 R2 就用 R2，否则读 `HIST_BASE` 指向的 GitHub
`data` 分支，两者都没有就在面板提示"历史数据未启用"，其余功能完全不受影响。

R2 快，但开通要绑卡；GitHub 零配置零成本，回源慢一点（首次约 200ms，
之后走边缘缓存 6 小时）。`/api/status` 会告诉你当前用哪个源、数据截止哪天。

## 四、自选存哪、怎么搬

存在 Workers KV，按**每台浏览器的匿名编号**分桶，几 KB。编号在首次打开时本地生成
（`u` 开头），存在 `localStorage.etfUid`。

| 动作 | 行为 |
|---|---|
| 打开页面 | 先渲染 localStorage（不等网络），再拉云端覆盖（只拉本机编号那个桶） |
| 增删自选 | 本地立刻生效，800ms 防抖后推云端 |
| 换设备 / 换浏览器 | **不会自动带过去**：新环境是新编号、空桶。用标题行「导入/导出」搬清单 |
| 没绑 KV | 静默降级为纯 localStorage，表头不显示「云端」标记 |

**为什么删掉了「一条链接换设备」（2026-11-08）。** 早先那版是「同步」按钮复制一条
`/?u=你的编号` 给另一台设备打开。问题在于那条链接本身就是写权限——本来发给自己的，
顺手转给别人、贴进群里，对方加一只删一只都写进你的桶，你这边跟着变。为了搬一次家
留一个永久后门，不划算。现在 `?u=` 参数完全不再读，迁移只走文本。

**导入导出的规则：**

- 导出：把当前自选拼成 `510300,513180,...` 一行，复制到剪贴板；
- 导入：只认 5~6 位数字，逗号、空格、换行、`sh` 前缀、名称里的汉字都当分隔符；
- **只追加，不覆盖**：重复的跳过，全市场里找不到的（比如 5 位港股代码）计入
  「未收录」不导入。所以误点两次不会把清单翻倍，也删不掉现有自选。

**一个容易踩的坑**：GET 必须区分「从没写过」和「写了个空数组」。
只返回 `list:[]` 的话，你在 A 设备清空自选，B 设备打开会以为云端没数据、
用本地列表重新推上去，删掉的标的全复活。所以接口返回额外带一个 `exists` 字段：

```json
{"ok":true,"exists":true,"list":[]}    // 用户清空了 → 其他设备跟着清空
{"ok":true,"exists":false,"list":[]}   // 从没写过 → 用本地列表初始化
```

同理，云端有数据时**不做并集**——并集分不清"新增"和"别处已删"。

## 五、部署

分两步：先让页面跑起来，再开历史 K 线和自选云端存储。
第一步不需要任何存储，五分钟能完。

### 5.1 第一步：跑起来

**A. 网页粘贴（最快，不装任何东西）**

1. https://dash.cloudflare.com → **Workers & Pages** → **Create** → Hello World → Deploy
2. **Edit code** → 全选删除 → 粘贴 `dist/worker.js` 全部内容 → **Deploy**
3. 访问 `https://<名字>.<子域>.workers.dev`

变量和 KV 也能在控制台加（见 5.2 末尾），所以这条路能走完全部功能。

**B. 命令行（推荐，配置写进 wrangler.toml，改起来有记录）**

```bash
cd worker
npm install -g wrangler
wrangler login
wrangler deploy
```

### 5.2 第二步：开历史 K 线和自选云端存储

**历史数据：默认不用 R2**

Worker 支持两种数据源，`histSource()` 决定优先级：

```js
function histSource(env) {
  if (env.BUCKET) return 'r2';        // 绑了 R2 就用 R2
  if (env.HIST_BASE) return 'gh';     // 否则读 GitHub 的 data 分支
  return null;                        // 都没有 → 历史面板标记未启用
}
```

**仓库必须是公开的**：`raw.githubusercontent.com` 对匿名请求读私有仓库一律返回 404，
jsDelivr 也不服务私有仓库。要么仓库公开（零配置），要么配一个只读令牌
（`wrangler secret put GITHUB_TOKEN`），Worker 会自动改走 `api.github.com` 取原始字节——
`Accept: application/vnd.github.raw` 让接口直出文件内容，不做 base64 解码，
否则 36KB 解一遍就吃掉几十毫秒 CPU，免费版（10ms）直接超限。

默认走 GitHub：Actions 每天把 `dist/hist/` + `manifest.json` 推到仓库的 `data` 分支
（每次都是孤儿单提交 + `--force`，所以仓库体积稳定在 62MB，不会一天涨一份）。
Worker 只需一个变量指过去：

```toml
[vars]
HIST_BASE = "https://raw.githubusercontent.com/你的用户名/etf-board/data"
```

想改回 R2（更快，但要绑卡开通）：

```bash
npx wrangler r2 bucket create etf-data
```

```toml
[[r2_buckets]]
binding = "BUCKET"
bucket_name = "etf-data"
```

绑了 R2 之后 `HIST_BASE` 自动失效，不用删。

**自选：KV（免费，不用绑卡）**

```bash
npx wrangler kv namespace create WATCH
```

命令会打印 `id = "xxxx"`，填进 `wrangler.toml`：

```toml
[[kv_namespaces]]
binding = "WATCH"
id = "上一步打印的 id"
```

**重新部署**

```bash
npx wrangler deploy
```

**验证**

访问 `https://<你的域名>/api/status`：

```json
{"ok":true,
 "bindings":{"r2":false,"kv":true,"gh":true},
 "hist":{"source":"gh","last_trade_date":"2026-11-04","codes":1717,"format":"ETH1","cols":17}}
```

`hist` 为 null 说明两种源都没配；`hist.error` 说明配了但没数据，去跑一次 Actions。

> 用网页粘贴部署的话，变量在 **Settings → Variables and Secrets** 加，
> KV 在 **Settings → Bindings** 加，效果一样。

### 5.3 GitHub Actions：不需要任何 secret

只有一件事要开：仓库 **Settings → Actions → General → Workflow permissions**
选 **Read and write permissions**。

因为发布数据用的是 Actions 内置的 `GITHUB_TOKEN`，往自己的 `data` 分支 push，
workflow 里已经声明了 `permissions: contents: write`。

然后 Actions 页面点 **Run workflow** 手动跑一次，约 15 分钟。

跑完仓库会多一个 `data` 分支，里面是：

```
data/
├── hist/510300.bin     1717 个，每个约 36KB
└── manifest.json       字段清单 + 最新交易日
```

### 5.4 Deno Deploy（没有 10ms 限制，但没有历史面板）

```bash
cd worker
deno install -gArf jsr:@deno/deployctl
deployctl deploy deno/main.ts
```

或在 https://dash.deno.com 建 Playground，粘贴 `deno/main.ts` + `src/index.js`
+ `src/page.js` + `src/idx_data.js`。

> Deno 没有 R2 / KV 绑定（`env` 传的是 `{}`），所以历史面板和自选云端存储会自动降级关闭。
> 要这两样就用 Cloudflare。

### 5.5 本地预览（不部署）

```bash
cd worker
node build.mjs && node dev_server.mjs     # → http://127.0.0.1:8899
```

`dev_server.mjs` 会给 Worker 塞一套 mock：**R2 读本地 `../dist`，KV 存进程内存**。
所以历史面板和自选云端存储在本地都能完整走通，不用为了看一眼 K 线先部署。

## 六、免费平台横向对比（2026-11 核实）

| 平台 | 请求额度 | CPU 预算 | 单请求上限 | 会休眠 | GBK 解码 | 对象存储 |
|---|---|---|---|---|---|---|
| **Cloudflare Workers** | 10 万/天 | 10ms × 请求 | **10ms** ⚠️ | 否 | ❌ | ✅ R2（10GB，出站免费） |
| **Deno Deploy** | 100 万/月 | **15 CPU 小时/月** | 无硬限制 | 否 | ✅ | ❌ 需外部 |
| Vercel Hobby | 100 万调用/月 | 4 CPU 小时/月 | 60s 执行 | 冷启动 | ✅ | ❌ 需外部 |
| Netlify Free | 12.5 万调用/月 | — | 10s 执行 | 冷启动 | ✅ | ❌ |
| Fly.io | — | — | — | — | — | ❌ 2024 起无免费档 |
| HuggingFace Spaces | — | — | — | **会睡** | ✅ | ❌ 不适合盯盘 |

**本项目的实际 CPU 消耗**：冷拉全量约 190ms，60 秒一次 → 约 **2.3 CPU 小时/月**。

- Deno 的 15 小时 → 富余 6 倍，但拿不到 R2 / KV 绑定
- Workers 的 10ms/请求 → 单请求卡死，只能靠「缓存命中 2.2ms」绕
- 历史数据不占 Worker 的 CPU：62MB 的 bin 放 GitHub 或 R2，Worker 只做透传

**结论：选 Cloudflare Workers。历史数据默认放 GitHub（不绑卡），
想要更快再开 R2——只是存储位置不同，Worker 代码不用改。**

## 七、Workers 的 10ms 是怎么绕过去的

全量 1717 只的处理成本实测（Node 环境）：

| 步骤 | CPU |
|---|---|
| `JSON.parse` 0.6MB | 3.4ms |
| **分类 1717 次（字符串 includes）** | **10.3ms** |
| 排序 1717 条 | 1.2ms |
| 纯字符串拼接 20 页 | 0.7ms |

常规写法光分类就 10.3ms，**必然超限**。所以：

1. Worker 只把 20 页文本拼成一个 JSON 数组字符串**直接透传**（0.7ms，不解码）
2. `JSON.parse`、字段映射、分类、排序、筛选、K 线绘制 **全部在浏览器做**
3. 加 `caches.default` 边缘缓存，跨 isolate 共享，TTL 5 秒

实测：**缓存命中 2.2ms**（从 34.9ms 降下来）。

历史数据走同一条思路：Worker 只 `bucket.get()` 后把流原样返回，一个字节都不解析。
边缘缓存 6 小时——历史数据一天只变一次。

如果日志出现 `1102 Worker exceeded CPU time limit`，按顺序：

1. `src/index.js` 的 `TTL` 从 `5` → `10`
2. `SINA_PAGES` 从 `20` → `12`（覆盖约 1200 只）
3. 换 Deno Deploy（放弃历史面板），或升级 Workers Paid（$5/月，CPU 30s）

## 十、数据存在哪

| 数据 | 存在哪 | 活多久 | 跨设备 | 跨实例 |
|---|---|---|---|---|
| 实时行情 `L1` | Worker 进程内存 | 5 秒 | ❌ | ❌ |
| `/api/all` 响应 | Web Cache API | 5 秒 | ✅ | ✅ 同 region |
| **自选列表** | **Workers KV**（一个 key） | 永久 | ✅ | ✅ |
| **历史日线** | **GitHub `data` 分支**（1717 个 bin，62MB），或 R2 | 永久 | ✅ | ✅ |

自选在 KV 之外还有一份 localStorage 副本：先把本地那份画出来，再用云端覆盖。
网络慢的时候不至于盯着空白表格等。

### 存储成本

**默认方案（GitHub）**：`data` 分支放 1717 个 bin + manifest，共 62MB。
每次 Actions 都是新的孤儿提交 + force push，旧提交不可达，仓库体积稳定。
完整 Parquet（993MB）只留在 Actions 的临时目录里，不回传——回测要在本地重跑
`alpha/compute.py`，不依赖线上那份。

**可选方案（R2）**：免费额度 10GB 存储 / 100 万 Class A / 1000 万 Class B 每月 /
出站全免。开起来后 `HIST_BASE` 自动失效，优先读 R2。

为什么不把 1GB Parquet 也传上去：Parquet 是整文件格式，改一个字段就得重写整个文件，
每天全量重传是纯浪费。页面只需要 `hist/`，回测只需要本地跑一次。

## 盯市页面的两次加法（2026-11-07）

### 一、板块地图：把「点」拼成「面」

此前页面上 1719 只 ETF 全是散点——榜单能排序、能筛选，但要拼出「今天钱在往哪条线走」，
得自己一只只翻。行业标签只用来过滤，没有行业之间的强弱比较。

新增一栏放在「今日变化」之前，12 个板块、每个方块给三件事：成交额加权涨跌幅、
上涨指数占比、成交额相对值。

**按跟踪指数聚合，不按 ETF 平均。** 中证A500 有 40 只、沪深300 有 29 只，
直接对 ETF 求平均，权重会被「发行数量」决定，看到的不是轮动而是发行节奏。
所以先归到指数（一个指数一票），再归到板块。指数涨跌幅取组内成交额最大的那只
（同指数各只本该一致，取大的是避开新发份额的跟踪误差）；成交额是**求和**，
那是真实发生的钱。

板块划分 12 个：半导体 / 人工智能 / 软件信创 / 通信传媒 / 医药 / 新能源 /
军工 / 金融 / 消费（含农业）/ 资源 / 制造基建 / 公用环保。按指数名关键词匹配，
247 个跟踪指数里 138 个能归位，其余 109 个是宽基（本来就不该进板块）。

顶部给三个读数：最强板块、最弱板块、**分化度**（最强减最弱）。
分化大＝结构性行情，分化小＝普涨普跌——这是「轮动」和「一起动」的分界，
比单看涨幅有用。点击方块展开该板块下的指数明细，再点行进 K 线。

### 二、盘中提醒：从「我去看」到「有事叫我」

盯市页此前只有异动列表，要自己刷新才看得见。新增自选级别的提醒，三类触发：

| 类型 | 默认阈值 | 去重 |
|---|---|---|
| 当日涨跌幅 | ±2.0% | 每只每天一次 |
| 3 分钟急变 | ±0.8% | 同一只 10 分钟冷却 |
| 溢价/折价 | ±2.0% | 同一只同一档 30 分钟冷却 |

只扫自选，不扫全市场：432 只每 5 秒扫一遍，一天能弹几百条，弹到第二次就没人看了。

**能力边界写在明处**：这是页面内提醒，标签页关掉就没了。页面在后台时用系统通知
（需手动授权）+ 标题加前缀；不做「假装是推送」。真要 7×24 得配 Web Push
（VAPID + 订阅端点持久化）或走企业微信机器人。

阈值可改，存在 localStorage；提醒记录不落盘，刷新页面即重置。

### 没做的

- **板块的「较昨日」维度**：现在只有当日横截面强弱，看不出放量还是缩量。
  要做需要历史成交额，得在 Worker 端加接口，前端一次请求拿 12 个板块的昨日值。
- **板块层面的资金流**：ETF 的净申购要用份额变化估，`shares.db` 有数据但没接进来。

## 第三次加法（2026-11-07）：全市场提醒 + 板块资金占比

### 一、提醒从「自选」扩到「全市场」

技术上没有难度——1719 只 ETF 循环一遍，60 秒一次，纯算术。**难的是信噪比。**

自选 20 只，一天越线三五次，逐只弹报得起。全市场按同一阈值逐只弹，
在 2026-11-06 那种日子里命中 **750 只**。弹到第二次就没人看了，等于没做。

**池子先按跟踪指数去重**（2026-11-07 补）。1719 只里 1202 只在跟别人跟踪同一个指数，
日内涨跌幅几乎一样——全量扫的直接后果是前 3 名被同一指数的克隆占满：20 只 A500
一起涨 3%，榜单给不出任何信息。改成只扫「每组的代表标的」（成交额最大那只），
池子从 1719 降到 468 只（247 个指数组 + 221 只没抓到跟踪标的、判断不了重复的），
一只一个指数，榜单才是「哪个方向在动」。没映射的那 221 只不排除——宁多扫一只，
也不要把一只没人跟的票静默藏掉。

所以 `alertScanAll` 走 `alertPool()`（去重 + 剔除停牌/债券/货币），不是 `DATA`。
汇总标题也带上了池子大小（「全市场 468 只中 12 涨 45 跌」），否则「12 涨」会被读成
「1719 只里只有 12 只在涨」，差着一个数量级。

所以两个范围用两套说法：

| | 自选（5 秒） | 全市场（60 秒，468 只） |
|---|---|---|
| 当日涨跌幅 | 逐只弹，当日一次 | 只弹「当下最极端的前 3 名」，且当日每只只报一次 |
| 汇总 | 无 | 每 5 分钟一条：多少涨多少跌 + 领涨领跌前三 |
| 3 分钟急变 | 有 | **没有** |
| 溢价 | 逐只弹 | 1.5 倍阈值才弹，60 分钟冷却 |

**3 分钟急变在全市场直接不给**：数据 60 秒一刷，3 分钟窗口只有 3 个采样点，
算出来的「急变」是采样误差不是行情。给一个做不准的指标，比不给更糟。

**极端名单只认前 3 名**，不是「所有超过 2 倍阈值的」。这个差别在跑第一版时才看出来：
按「所有」报，每轮弹出前三名，下一轮它们被冷却挡住、就漏出第 4/5/6 名——一路漏到底，
等于没有上限。限定在前 3 名内，超出的只进记录。

越线比例超过 25% 时汇总换口径：「750 只跌超 2%」已经不是「哪些在动」，
是「全市场在跌」，标题直接写「普跌 · 全市场 2 涨 750 跌 越过 2%」。

新增「今日提醒」记录（右上角条数，点开就是列表）。浮层只停 9 秒，
全市场模式下记录才是主要出口。面板开着时不再弹浮层——两者都在右上角，
会正好盖住列表，而且列表本来就是浮层的完整版。

### 二、板块地图加「资金占比」变化

回答的是「钱在进还是在出」，原来只有横截面强弱，答不了。

**口径（照着能复算）：**

| 环节 | 具体是什么 |
|---|---|
| 数据 | `/api/all` 里每只 ETF 的 `amt`＝当日累计成交额（新浪 `amount` 字段，单位元） |
| 谁参与 | 按**跟踪指数名**归类（不看 ETF 简称）；宽基、风格、债券货币、商品四类三组都不进 |
| 指数聚合 | **一个指数只出一票**：成交额和涨跌幅都取代表标的（同指数里成交额最大那只） |
| 分子 | 该板块下各跟踪指数的代表标的成交额之和 |
| 分母 | **本组「行业格」**成交额合计，主题格不进分母。2026-11-07 收盘：A股 532.1 / 港股 373.2 / 跨境 210.9 亿（含中韩半导体主题 121.3） |
| 例 | 半导体 194.5 亿 ÷ A股行业 495.0 亿 = **39.3%** |
| 变化 | 当前占比 − **上一交易日收盘**占比（同组内各自占比），单位百分点 |

**三组各自算分母（2026-11-07 改）。** 之前 A 股和港股共用 579 亿分母，半导体 175 亿
算出来 30.3%——既不表示 A 股内部分布（真实 39.3%），也不表示港股（港股没有半导体）。
跨市场涨跌幅同样不可比（汇率、交易时段、投资者结构），混排出来的「最强/最弱」没有
交易含义。现在组头各报各的强弱，顶部只报三组的总量。

**格子怎么划。** A 股 18 个行业格 + 2 个主题格，骨架是申万一级，按 ETF 实际供给合并/拆分：

| 本项目的格子 | 申万一级对应 |
|---|---|
| 半导体 | 电子（半导体单列：ETF 供给占电子类绝大多数，合并等于只剩半导体） |
| 电子 | 电子（面板、元件、消费电子、光学、安防、物联网） |
| 通信 | 通信（光模块、CPO、5G、运营商、电信） |
| 传媒 | 传媒（游戏、影视、动漫、出版、广告） |
| 计算机 | 计算机（软件、信创、云计算、大数据、网络安全、金融科技） |
| 医药 | 医药生物 |
| 光伏 | 电力设备（**单列**：光伏 ETF 7.8 亿，混在「新能源」里会被电池和储能盖住） |
| 电池储能 | 电力设备（电池、储能、锂） |
| 汽车 | 汽车（含智能驾驶、零部件、汽零） |
| 军工 | 国防军工（含航天航空、船舶、卫星、通用航空） |
| 金融 | 银行 + 非银金融 |
| 消费 | 食品饮料 + 家电 + 纺服 + 轻工 + 商贸零售 + 社服 + 美容护理 |
| 农业 | 农林牧渔（猪周期是独立主线，混进「消费」看不出来） |
| 资源 | 有色金属 + 煤炭 + 石油石化（**上游**） |
| 材料 | 基础化工 + 钢铁 + 建筑材料（**中游材料**） |
| 机械 | 机械设备（工程机械、机床、机器人、电网设备） |
| 地产基建 | 房地产 + 建筑装饰 |
| 公用环保 | 公用事业 + 交通运输 + 环保 |

**主题格：人工智能、新能源。** 这两个不是申万一级行业，是跨行业主题——
中证人工智能主题的成分是半导体（算力芯片）+ 通信（光模块）+ 计算机（AI 应用），
新能源指数是光伏 + 电池 + 风电 + 电网。它们和上面的行业格**是同一批股票**，
所以：

- 单独排在每组末尾，一条虚线隔开，边框也用虚线；
- **不计入占比分母**（A 股分母 495 亿不含 AI 27 亿、新能源 10 亿）；
- 不参加组头的「最强/最弱/分化」排名（否则会出现「AI 最强、半导体也最强」）；
- 格子上不报百分比——121.3 ÷ 89.7 会算出 135%，这不是错，是「重叠」的定义，
  报了反而像分母算错。

为什么保留而不并进计算机：AI 是独立的需求叙事（算力资本开支），并进去就看不见了；
但必须让读者一眼知道它不能和行业格相加。

港股 7 格用同一套行业口径，另加「港股红利」；跨境不做行业，只按国家/地区：

| 组 | 格子 |
|---|---|
| 港股 | 港股互联网 / 港股科技 / 港股医药 / 港股金融 / 港股消费 / 港股汽车 / 港股红利 |
| 跨境 | 美国 / 日本 / 德国 / 欧洲 / 东南亚 / 沙特 / 巴西 / 全球 ＋ 主题：中韩半导体 |

**中韩半导体（513310）也是主题，不进跨境分母。** 它跟踪「中证韩交所中韩半导体」，
一半仓位是 A 股半导体、一半是韩国，一天成交 121 亿——比美国格（72.8 亿）还大。
放进「韩国」格会让韩国凭空变成跨境第一大市场，而它根本不是「配置韩国」，
是 A 股半导体行情的跨境映射。单列之后，跨境地区合计 89.7 亿，美国占 81.2%。

**空格子不渲染。** 港股「地产」、跨境「印度」这类当天一条指数都没成交的格子直接不出，
否则三十多个格子里一半写着「—」。

**钢铁、建材为什么在「材料」、不在「资源」也不在「制造基建」。** 申万里有色金属、
煤炭、石油石化是上游（采掘/大宗），基础化工、钢铁、建筑材料是中游材料，本来就是
三组不同的行业。原来并进「资源」，读起来像上游涨价，实际是地产链，方向会读反。
也没并进「制造基建」——机械设备和房地产在申万各有独立一级，硬合在一起会把
「机器人涨、地产跌」抹平成 0。

**跨境为什么一度只有 40 亿（2026-11-07 已修）。** 用户指出「标普消费 ETF 没提到、跨境不全」，
查下来不是关键词的问题，是映射表的生成脚本：`pipeline/gen_idx_data.mjs` 为了省体积，
只保留「2 只及以上同指数」的组，**229 个单只指数被整组丢掉**。而这些单只指数恰恰是
大品种——中概互联网 513050、港股创新药 513120、半导体 512480、通信 515880、
中韩半导体 513310、标普消费 159529 全在里面。`ix` 变成 null 之后，板块地图第一行
`if (!x.ix) continue` 直接把它们扔了：跨境少 160 亿、港股少 183 亿、通信少 28 亿、
半导体少 55 亿。单只组一点也不多余——去重只需要组内成员，一个成员也是成员。
恢复后 `idx_data.js` 从 19.7KB 涨到 27.6KB（gzip 约 +4KB）。

同一轮还补了三处：
- 没有跟踪标的字段的新发 ETF，用简称当临时指数名（159516 半导体设备一天 37 亿，原先也丢）；
- 关键词漏了「东证」（日本东证 3 亿）和「酒」（中证酒 6.2 亿，原先落在消费外面）；
- 日档的键写的是板块名、读的是「组码/板块名」，两边永远对不上——基准攒一年也画不出箭头。
  已统一成 `a/半导体` 形式，日档版本升 `v6`。

**三条硬规则（都踩过坑）：**

1. **匹配对象是指数名，不是 ETF 简称。** 「互联网ETF」的简称里没有「港股」，但它跟踪
   「中证港股通互联网」——按简称判会把它算成 A 股行业。所以港股关键词**先于 A 股匹配**，
   命中即进港股组，且不再进 A 股组（否则「中证港股通信息技术综合」会被「信息技术」
   抓进 A 股计算机）。
2. **「恒生A股XX」不是港股。** 恒生编了一批 A 股行业指数（恒生A股电网设备），
   判定前先把「恒生A股」四个字摘掉，否则会被「恒生」抓进港股组。
3. **商品的纯价格指数三组都挡在外面。** 黄金9999 一天 37.8 亿，进「资源」会占 68%，
   把有色/化工全盖住。挡的是 `黄金9999 / 上海金 / 白银 / 原油 / 豆粕 / 商品`，
   「中证沪深港黄金产业股票」是黄金股，仍算资源。港股宽基（恒生指数、恒生国企、
   港股通50、恒指港股通）也不进——它们是港股整体，进「港股科技」之类会把格子涨跌幅
   变成恒指涨跌幅。

**三组可折叠。** 三十多个格子同屏太挤：默认只展开 A 股，港股/跨境收起时组头那一行
就是摘要（几个板块、合计成交额、最强、最弱、分化、涨跌家数）。展开/收起状态写
`localStorage`，下次打开还是上次的样子。折叠只切 class 不重绘，避免滚动位置弹回顶部。

### 二点五、占比走势与集中度（2026-11-08）

板块地图原先只有「今天」：半导体占 39%。但 39% 可能是刚启动，也可能是一年高位——
这两个判断对应的动作完全相反，而页面上没有任何东西能区分。

**做法是把同一口径回算到过去 250 个交易日。** `pipeline/gen_sec_hist.mjs` 读
`data/etf.db` 的 150 万行日线，按页面现行口径（每指数只算成交额最大的那只、
三组各算各的分母、主题不进分母）算出每天 36 格的占比，写成 `worker/src/sec_hist.js`
（31KB，gzip 后约 8KB）。

| 位置 | 内容 |
|---|---|
| 格子 tooltip | 「占 A 股板块 39.3%，近一年 98 分位」——不点开也知道在什么位置 |
| 点开格子 | 一条 250 日占比曲线 + 当前值 / 分位 / 区间 / 中位线 |
| A 股组头下方 | 全 A 集中度 × 宽度四象限散点（见二点六） |

**四象限的口径不是这一节的 ETF 数据。** 集中度 / 宽度那张散点用的是**全 A 个股**
（东财 128 个行业），不是上面这 36 格的 ETF 成交额——两者差 30 倍（532 亿 vs 16576 亿），
混着看会得出完全相反的结论。为什么必须分开，见二点六第一节。

**曲线末端怎么跟到最新。** 静态基线只到生成那天，不接增量的话一周后就停在原地
（图上看着「没变化」，实际是没数据）。`secdaily` 日档每天收盘存一份 36 格成交额，
前端用它把尾巴接上：日档只有成交额，占比按当天组内行业合计现算。日档留 90 天
（约四个半月），更早的部分由 250 天基线覆盖，正好接得上。

**末端那一段虚线。** 历史库到上个交易日（比如周五），页面上的值是今天——中间可能
隔了周末或几天没跑数据。补上去的那一段单独画虚线，不假装这几天有连续报价。

**日档现在由 Actions 每天回算，不再依赖有人打开页面。** 早先是浏览器在收盘后写 KV
（`maybeSaveSecDaily`），没人打开那天就没有记录：漏一天，资金箭头就跨两天比；漏几天，
箭头直接消失。现在 `gen_sec_hist.mjs --json-only` 在 Actions 里跟着 ETF 日线一起跑，
产出 `dist/sec_daily.json`（90 天 × 36 格的**绝对成交额**，不是占比——两天的分母不同，
存占比减不出东西），推到 data 分支，`/api/secdaily` 主读它、KV 只做兜底。

**`gen_sec_hist.mjs` 什么时候还要手动跑。** 它同时产 `worker/src/sec_hist.js`（250 天
占比曲线，内联进页面）。这份只在「重新部署」时需要，建议季度一次。日档那份每天自动更新，
不用管。

**数据源是 `dist/hist`，不是 `data/etf.db`。** 这一条是踩过坑改的：`etf.db` 在
`.gitignore` 里，只有手动跑 `import_etf.mjs` 才会往前走，而 `dist/hist` 是 Actions
每天 16:35 现生成的、页面 K 线用的同一份文件。拿 db 当唯一来源，基线就会永远停在
「上次手动跑的那天」，而页面上「今天」的点是实时的——2026-11-08 那天就出现过
基线停在 11-03、云和今天差三个交易日。现在默认读 `dist/hist`（ETH1 二进制，
1719 只 × 500 天，约 1 秒），显式传 `data/etf.db` 才走老路（离线回溯、对账用）。

### 二点六、全 A 集中度 × 宽度：四象限散点（2026-11-08，口径重做）

单个数字没有参照就只是数字。24% 是「钱压得很紧」还是「这一年常这样」，
只看那一行看不出来；而它落在平面上的位置，一眼就能读。

**这一节的第一版是错的，先说错在哪。** 初版用 A 股 18 个行业格的 **ETF 成交额**
算 TOP3 占比，得出 58.7%，还煞有介事地给了分位。问题是这个 58.7% 不是市场结构，
是分母造出来的：

| | ETF 口径（旧） | 全 A 个股口径（新） |
|---|---|---|
| 分母 | 只覆盖有 ETF 跟踪的 18 个格，532 亿 | 全部 128 个东财行业，16576 亿 |
| 集中度 | 58.7% | **24.1%** |
| 宽度 | 203 个指数 24 个涨 = 11.8% | 128 个行业 9 个涨 = 7.0% |
| 同日个股涨跌 | — | 716 涨 4431 跌（12.9%） |

更要紧的是口径本身：ETF 二级市场成交是**份额转让**，不产生股票成交。半导体 ETF
一天 200 亿和半导体个股一天 2245 亿是两套钱，前者代表不了后者。银行、汽车零部件、
通用设备这些没有 ETF 的行业，在旧口径里根本不存在。

**新口径。**

| 轴 | 口径 |
|---|---|
| 纵轴 | TOP3 行业成交额 ÷ 全部行业成交额（东财 128 个二级行业） |
| 横轴 | 当日上涨行业数 ÷ 有成交行业数 |
| 虚线 | 纵轴取近一年中位（22.2%），横轴固定 50% |
| 同象限 | 近一年有多少天和你今天站在同一格（今天 26%，65/250） |

行业名单以**个股的 `f100` 字段**为准，一只股票只归一个行业。不用东财板块列表自己推，
因为那张表里「电子」和「半导体」并列（496 个，含三级嵌套），直接加总会把同一批股票
算两遍——加出来 38293 亿，是全 A 成交额的 2.3 倍。

**历史怎么来。** 个股历史要 5563 次请求，不可行。改用行业板块 K 线：128 个行业
× 1 次请求 ≈ 20 秒，`pipeline/gen_mkt_hist.mjs` 一次跑完 250 天。板块成交额就是
板块内个股成交额之和（11-06 实测：128 个行业合计 16576 亿 = 全 A 个股合计 16576 亿，
分毫不差），两套口径能对上。

**当天的点。** `/api/mkt` 拉板块列表算，4 页 × 100 条，约 0.5 秒，60 秒边缘缓存。
翻页的排序键必须是 `fid=f12`（板块代码）——用成交额排序，盘中每秒都在变，第 2 页
会混进第 1 页出现过的、又漏掉另一批，实测只捞到 98/128 个行业。
顺带把 `f104`/`f105`（涨跌家数）加总，得到「767 涨 4793 跌」，补上行业层面看不见的那层。

**为什么点云是两团、中间空。** A 股要么普涨要么普跌，宽度天然两极，250 天里
0–20% 和 80–100% 最多，40–60% 反而少。这不是画错了，图上那句小字专门写了。

**为什么用行业不用个股数宽度。** 个股家数更贴近「市场宽度」的经典定义（12.9% vs 7.0%），
但个股没有历史——拿不到 250 天前「多少只股票在涨」。行业有 K 线，能和散点云同口径。
两个数都给了：卡片上是行业（7%），说明行里附个股家数。

**历史不再靠手动跑。** `gen_mkt_hist.mjs` 每天在 GitHub Actions 里跑（收盘后 16:35，
和 ETF 日线同一批），产出 `dist/mkt_hist.json` 推到 data 分支；`/api/mkt` 顺手把它
一起返回，前端覆盖掉内联的那份。内联的只是首屏兜底——不这么做，一个月不重新部署，
散点云就停在发布那天，而「今天」每天往里走。

### 二点七、标题下的数据体检
`#secMeta` 一行：`36 格 · 279 个指数有成交 · 报价 1719 · 无跟踪标的 14 只（43.5亿）`。

这一行不是新功能，是**防复发**。此前映射表生成脚本为了省 11KB 把 229 个单只指数整组
丢掉，跨境少 160 亿、港股少 183 亿，页面上完全看不出来——数字照样显示，只是小了一截。
现在覆盖率写在标题下：多少格、多少指数、多少只有报价、多少只进不来、进来了多少亿。

「无跟踪标的」只数**本该进图却进不来**的（行业/主题 + 跨境）。宽基、债券、货币、
商品本来就不进板块地图，把它们算成「漏掉」会把 592 亿的债券货基写得像事故。

**表外有 5257 亿，都是本就不该进的。** 2026-11-07 收盘全市场 6373 亿，进板块 1116 亿，
剩下：债券 3020、货币 548、宽基 1039、商品 127、风格（红利/价值/现金流）与港股宽基若干。
宽基那 1039 亿里创业板指 138、科创50 130、中证A500 68、沪深300 52。
真正的「该进没归类」只剩零星几个（中证科技龙头 1.4 亿这类跨行业主题）。

**明细要全列，不能截断。** 原先只显示前 8 个指数，新能源这种十几条线的板块里，
光伏是否出现在列表取决于它当天涨没涨——那是错的。现在全部列出，两列排，点一行看 K 线。

**为什么用占比不用绝对成交额。** 盘中拿今天的累计额直接比昨天全天，是被时间进度
污染的：10:30 的 3 亿和昨天的 8 亿不是一回事，会得出「缩量」的错误结论。
占比（板块 ÷ 行业板块合计）里分子分母同受时间进度放大，比值基本抵消。

**为什么不用「昨日同期」这个更准的口径。** 没有历史分钟数据。新浪 minline 只有当天
（`kind=min` 无日期参数），东财 trends2 在本项目里实测连不通（见 `fetchMin` 注释）。
这条路堵死了，占比是能做的里面误差最小的。

口径写在格子的 `title` 里：占比 X%，较 MM-DD 收盘 ±N 个百分点。
基准是**上一交易日收盘**那一条，并且**从最近一天往前找第一条与当前不一致的日档**——
休市时看到的正是上一交易日收盘值，不跳过的话今天会跟自己比，恒等于 0。

为什么不取近 5 日均值（第一版）：均值要攒够几天才出数，「比一周平均高」也读不出
「今天钱在往哪挪」。只跟一个日终比，有一条日档就能出箭头，**盘中也能读**——分子分母
同受时间进度影响，比值基本抵消，「此刻累计占比 vs 昨日全天占比」仍有方向意义。

**两个存储约束**（都在 `maybeSaveSecDaily` 里）：
- 盘中不存：存进去的是半天的量，会污染基准
- 日期取「行情对应的交易日」：收盘后写当天，开盘前/周末打开则补记最近一个工作日；
  值与上一条几乎一致就跳过（长假、临时休市不会多出一条错位记录）

**为什么让前端 POST 存档，而不是服务端自己解析。** 全量快照是 600KB 原始 JSON，
在 Worker 里 parse 一次吃掉不少 CPU；而且板块划分（`SEC_DEF` 关键词表）在 page.js 里，
服务端再复制一份就会两边漂移。前端算完只 POST 三十二个数字。

代价是「今天没人打开页面就没有这天的记录」。第一版的条件是「15:00 之后才存、周末不存」，
等于基准只在「收盘后恰好有人打开」那天才落得下来；漏一天，箭头就跨两天比，漏几天直接
没有基准。日期改取**行情对应的交易日**（不是「今天」）之后，收盘后写当天、开盘前或周末
打开补记最近一个工作日，漏记的概率小了很多，但「没人打开」这件事本身还在。

**2026-11-08 彻底改成后台回算。** `pipeline/gen_sec_hist.mjs --json-only` 在 GitHub Actions
里跟着 ETF 日线一起跑，产出 `dist/sec_daily.json`（90 天 × 36 格的绝对成交额），推到 data
分支；`/api/secdaily` 主读这份，KV 退成兜底（Actions 挂了、文件还没发布时才用）。浏览器
那个 `maybeSaveSecDaily` 保留着，它现在是双保险，不再是唯一来源。

接口 `/api/secdaily`：GET 优先读 data 分支的 `sec_daily.json`（30 分钟边缘缓存），
KV（`sec-daily-v6`）兜底；POST 仍可写 KV 一天（同一天多次 POST 取最后一次）。

### 显示上踩的两个坑

**「0.1pt」铺满格子。** 第一版 12 个格子里 8 个写着 0.1pt/0.4pt。读数的人两天就学会
无视这一列，那这个指标等于没做。改成：变化不到 0.5 个百分点就留空。

**角标位置。** 第一版放在底部一行（`4/4 64.9亿 ↑6.0pt`），跟成交额离得很远，
红绿还跟涨幅的涨跌色打架。改到板块名右侧做角标，「-1.41%」配「↑6.0pt」
——价格在跌、钱在进，这个分歧一眼就能看到，这正是这个指标的价值。

### 没做的

- **绝对放量倍数**（今天比昨天同时刻放了几倍）。要它必须有历史分钟数据，见上。
- **盘中「昨日同期」对比**。只有收盘日档，所以盘中比的是「此刻累计占比 vs 昨日全天占比」。
  想比同期得有历史分钟数据，同样堵在这。
- **板块资金流**（净申购）。得用份额变化估，`shares.db` 有数据但没接进来。
